# Filter Registry

The registry is the canonical source of supported hotel-search filters.

## Filter definition

Prefer explicit fields such as:

```json
{
  "id": "room.size_m2",
  "type": "range",
  "description": "Room floor area",
  "aliases": ["room size", "large room", "spacious room"],
  "unit": "m2",
  "bounds": {"min": 0},
  "conflicts_with": []
}
```

Supported filter types must include at least:
- `boolean`;
- `range`.

Use stable canonical IDs. Never persist free-form filter IDs generated by an LLM.

## Validation

Validate deterministically:
- filter ID exists;
- type matches the registry definition;
- unit is valid;
- ranges and bounds are valid;
- allowed enum/value constraints are respected;
- conflict metadata references valid canonical IDs.

Conflict handling belongs to application/domain validation, not the LLM.

## Retrieval for large registries

For a 1000+ filter catalog, do not inject the entire registry into each prompt.

Initial approach:

```text
filters.json / filters.yaml
 -> aliases / keywords
 -> candidate filters (~20-50)
 -> LLM extraction
```

Keep retrieval deterministic and simple first. Only introduce PostgreSQL + pgvector or other semantic retrieval infrastructure when a concrete production requirement justifies it.

## Bulk additions or edits

When adding many filters:
- preserve the existing schema and naming convention;
- avoid duplicate or semantically equivalent IDs;
- prefer concise, searchable aliases;
- define units/bounds explicitly for ranges;
- define conflicts explicitly where known;
- validate registry integrity after changes.

Do not invent unsupported business semantics. If filter meaning or constraints are unclear, keep the definition minimal rather than guessing.
